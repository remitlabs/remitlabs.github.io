An MCP security checklist that survives an audit

Five controls, in the order that matters, with the failure mode each one leaves open.

Prahalad Singh2026-11-0810 min read

Short answer: you need five controls — an inventory of every MCP server and tool, least-privilege credentials per server, a load-time gate with evidence, a log you can diff week over week, and a revocation path that reaches every machine. Each one is necessary. None of them is sufficient on its own.

Most MCP security advice is a list of product features. This is a list of failure modes, and the control that addresses each one. Where a control has a hole, the hole is stated.

Why MCP is a different surface from a dependency

An MCP server exposes tools to an agent. A tool call can read a file, query a database, send a message, or run a command. The model chooses the call from a description written in natural language, and the description is attacker-controlled if the server is third-party.

That creates three boundaries collapsing into one place:

  • Documentation — the tool description the model reads and trusts.
  • Code — the server implementation and anything it executes.
  • Authority — the credentials and permissions the server holds.

A package manager only ships code. MCP ships instructions the model obeys, plus the authority to act on them. That is why "we scan dependencies" does not cover this surface.

1. Inventory every server and every tool

Control: keep a list of every MCP server configured for every agent, the tools each one exposes, who added it, and when. Include project-local config, user-level config, and anything a plugin installed silently.

Why it matters: you cannot govern what you cannot name. In practice, teams find servers they did not know were configured — a database server added for one experiment, a browser automation server a contractor installed, two copies of the same server at different versions.

How to start: parse the MCP config files your agents use, resolve each server to a package and version, and store the result as a digest-bound record. Repeat it on a schedule, because config drifts.

What it leaves open: an inventory is a snapshot. A server can add a tool after you record it. Pair this with control 4.

2. Scope credentials per server, not per person

Control: every MCP server gets its own credential with the minimum scope it needs. No shared personal access token across five servers. No admin token because it was easier. Rotate on a schedule and on offboarding.

Why it matters: the blast radius of a compromised server is the scope of its token. A GitHub token with repo and workflow can do far more than a read-only token, and a database server rarely needs write access to production.

How to start: list each server, the credential it uses, and the scope. Anything with write access to production or the ability to change CI is a review item. Replace shared tokens with per-server service accounts.

What it leaves open: least privilege limits damage; it does not detect misuse. A read-only token can still exfiltrate everything it can read.

3. Gate the load, with evidence attached

Control: a server or skill does not reach the model until a policy decision says it may. The decision has four outcomes — allow, monitor, review, deny — and it carries the evidence that produced it: static findings, observed behavior when available, the digest, and the missing coverage.

Why it matters: a scan that produces a dashboard nobody reads is not a control. A gate is. The difference between "we scanned it" and "it could not load" is the difference between an alert and a boundary.

How to start: deny by default for new servers; allow known-good digests; require a second person for review-level loads; make the reason visible in the agent's error, not buried in a log.

What it leaves open: a gate is only as good as its evidence. If the only input is a static scan, a determined attacker can shape the artifact to pass it. That is why controls 4 and 5 exist.

The uncomfortable fact: Trail of Bits built four malicious skills in under an hour each and defeated ClawHub, skills.sh, and Cisco's scanners. A static scan is a filter, not a proof. Gate on it, but do not stop there.

4. Log tool calls and diff them week over week

Control: record which tools were called, by which agent, with what arguments (or a redacted summary), and what changed since the last review. Alert on new destinations, new tools, and new credential paths.

Why it matters: most incidents are changes, not static facts. A server that behaved for six months and then starts contacting a new domain is the signal. A one-time scan will never see it.

How to start: log at the proxy or the MCP router, not inside each server. Keep a normalized schema so you can compare. Send a weekly digest: new servers, changed tools, blocked attempts, skills that never fired.

What it leaves open: logging observes what reached the logging layer. A compromised host or a call outside the router is invisible. TLS bodies are usually opaque.

5. Keep a revocation path that reaches every machine

Control: a signed list of revoked or drifted artifacts, verified by every client, applied at load time and on the next sync. Removal must be reversible and recorded, and hand-installed copies must be surfaced rather than silently deleted.

Why it matters: security without a kill switch is theater. If a bad server ships to 40 laptops, "please uninstall it" is not a control. A signed feed that blocks the digest at load is.

How to start: define who can publish a revocation, how it is signed, how clients verify it, and what the SLA is. Test it: revoke a benign test artifact and confirm it is blocked on a second machine.

What it leaves open: a machine that never syncs never learns. Air-gapped environments need a mirror. A compromised client can lie about what it applied.

What none of this proves

A checklist is not a guarantee. Be explicit with your team and your auditor about the limits:

  • Scanners are bypassable. Public research has defeated every major marketplace scanner. Treat a scan as one input.
  • Behavioral observation is a sample. One canary run does not cover conditional triggers, other hosts, or the model's own reasoning.
  • Inventory is a snapshot. Drift is the norm, not the exception.
  • Revocation needs a sync. A machine that never checks in is outside the control.
  • Least privilege limits damage, not intent. A narrow token can still be abused within its scope.

The goal is not a clean bill of health. It is a chain of evidence and a reversible decision at each link: what is here, what it can touch, what changed, who approved it, and how to make it inert.
