An MCP security checklist for your team

Five checks for the servers your AI agents use, with practical steps and limits.

Prahalad Singh2026-11-0810 min read

Start by listing the MCP servers and tools your team uses. Give each server only the access it needs. Review what can load, record activity and establish a way to block a compromised version.

The checks below explain how to put those controls in place and what each one can miss.

What an MCP server can access

An MCP server gives an agent tools it can call. Those tools may read files, query databases, send messages or run commands. The model chooses tools using their descriptions. Review descriptions from third-party servers because their authors control that text.

Review the server's instructions, code and permissions together.

  • Instructions. The tool description the model reads.
  • Code. The server and anything it executes.
  • Access. The credentials and permissions the server holds.

Reviewing an MCP server includes its tool descriptions and credentials as well as its dependencies.

1. Inventory every server and every tool

Control: keep a list of every MCP server configured for every agent, the tools each one exposes, who added it, and when. Include project-local config, user-level config, and anything a plugin installed silently.

Why it matters: old experiments, plugin installs and different versions can leave unexpected servers configured. An inventory gives your team a starting point for review.

How to start: read your agents' MCP settings and record each server's package, version and content hash. Recheck regularly and after configuration changes.

What it leaves open: an inventory is a snapshot. A server can add a tool after you record it. Pair this with control 4.

2. Use separate credentials for each server

Control: give each MCP server a separate credential with the minimum permissions it needs. Replace shared personal tokens. Rotate credentials regularly and when someone leaves the team.

Why it matters: a compromised server can use the access its token grants. Review broad permissions such as GitHub repo and workflow, especially when the server only needs to read data.

How to start: list each server, the credential it uses, and the scope. Anything with write access to production or the ability to change CI is a review item. Replace shared tokens with per-server service accounts.

What it leaves open: a server can misuse even limited permissions. A read-only token can expose the data it can access.

3. Review what can load

Control: require an approval decision before a server or skill loads. Record whether it is allowed, monitored, held for review or denied. Include the version checked, findings, observed behavior and missing tests.

Why it matters: a review helps only when its result affects what the agent can load. Make the decision enforceable and visible to the user.

How to start: hold new servers for review. Allow the exact versions you approve. Require a second reviewer for uncertain cases and show the reason when a load is blocked.

What it leaves open: file checks can miss harmful code or instructions. Review later behavior and maintain a way to revoke an approved version.

A file scan can miss a harmful instruction or a trigger that activates later. Include missing coverage in the approval decision and keep a way to block the version after approval.

4. Log tool calls and diff them week over week

Control: record which tools were called, by which agent, with what arguments (or a redacted summary), and what changed since the last review. Alert on new destinations, new tools, and new credential paths.

Why it matters: a new network destination or newly exposed tool may need another review. Compare activity over time to spot changes after the initial scan.

How to start: record activity at the proxy or MCP router using a consistent format. Review new servers, changed tools, blocked attempts and unused skills each week.

What it leaves open: logging observes what reached the logging layer. A compromised host or a call outside the router is invisible. TLS bodies are usually opaque.

5. Keep a revocation path that reaches every machine

Control: a signed list of revoked or drifted artifacts, verified by every client, applied at load time and on the next sync. Removal must be reversible and recorded, and hand-installed copies must be surfaced rather than silently deleted.

Why it matters: a compromised version may be installed on several computers. A verified revocation list helps each client block the same version.

How to start: define who can publish a revocation, how clients verify its signature and how quickly it should apply. Revoke a harmless test version and confirm that a second computer blocks it.

What it leaves open: a machine that never syncs never learns. Air-gapped environments need a mirror. A compromised client can lie about what it applied.

Review the remaining limits

Tell your team and auditor what each check can miss.

  • Scans can miss harmful behavior. Read the findings together with their coverage and limits.
  • Behavioral observation is a sample. One canary run does not cover conditional triggers, other hosts, or the model's own reasoning.
  • Inventories need updates. Recheck the list when tools, settings or versions change.
  • Revocation needs a sync. A machine that never checks in is outside the control.
  • Limited permissions can still be misused. Review activity within the access you have granted.

Keep a record of what is installed, its permissions, version changes and approvals. Test the process for blocking a version across affected computers.
