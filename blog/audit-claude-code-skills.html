How to audit your Claude Code skills

A skill is documentation, code, and authority in one file. Here is how to see what is actually installed — and what to do about it.

Prahalad Singh2026-11-088 min read

Short answer: run npx @remitlabs/cli@latest start. It inventories every skill in the agent directories Claude Code uses, scans each one with 64 static rules, records a content digest, and opens a local dashboard with the highest-severity findings first. It does not install or modify anything, and it needs no account.

That is the whole procedure. The rest of this article explains what the output means, which four findings matter, and what to do about each one — including the parts the tool cannot prove.

Where Claude Code keeps skills

Claude Code can load skills from several places, and that is the first reason audits are hard: there is rarely one folder to check.

  • User-level skills — under your home directory, shared across projects.
  • Project-level skills — a .claude/skills directory inside a repository, which travels with the code.
  • Plugin and marketplace skills — installed through a plugin or copied from a registry such as skills.sh.
  • Other agents' directories — Codex, Cursor, and OpenCode each have their own locations, and most developers run more than one agent.

If you have been using coding agents for a year, the same skill often exists in two or three of these places. One copy is current; the others are whatever you copied six months ago. Nothing warns you.

Run the audit

$npx @remitlabs/cli@latest start

The first run discovers the agent directories it knows about, scans each skill, and starts a local app on 127.0.0.1:8787. On the machine this was built on, that produced:

123 skills across 4 agent directories
114 duplicate registrations
~15,238 tokens of skill text in eager mode
3 skills needing review
0 files modified

Those numbers are from one developer's machine, not a survey. Your fleet will differ. The shape of the result is what matters: most people find more skills than they expected, more duplicates than they expected, and at least one thing they did not know was there.

The four findings that matter

1. Risky patterns in the skill's own files

The static scanner looks for 64 high-signal patterns across SKILL.md and any scripts: curl … | sh, reverse shells, reads of ~/.ssh or .env, base64 blobs, hidden unicode, encoded instructions, approval-bypass phrasing, and more. A hit is a rule match, not proof of intent — but it is a reason to read that file before you let an agent load it.

2. Declared versus observed behavior

A skill's description says what it is for. Its scripts say what it can do. Those are different claims, and the gap is where incidents live. When Docker or Podman is available, Remit runs the skill in a disposable container with fake secrets and a logging proxy, then records what it actually touched: files written, network destinations, shell commands, credential paths.

That is one observed run, not a guarantee. A skill can behave differently on another host or after a conditional trigger. But "it declared no network access and opened a connection to an unknown host" is a concrete finding you can act on.

3. Duplicates and stale copies

The 114 duplicate registrations above are the least glamorous finding and often the most useful. Duplicates mean:

  • You are maintaining the same skill in three places.
  • At least one copy is stale.
  • A fix or a revocation may not reach every copy.
  • Your context budget is being spent on the same instructions more than once.

4. Context cost

Eager loading puts every skill's text in front of the model before it reads your prompt. In a 123-skill fleet, that measured ~15,238 tokens per prompt. On-demand routing through the MCP server measured ~150 tokens — the router exposes a short index and loads a skill only when it is relevant.

This is not only a cost problem. A prompt full of irrelevant skill instructions is a prompt full of distractors, and it makes trigger conflicts more likely.

What to do about what you find

The audit is the easy part. The useful work is the lifecycle that follows.

Pin what you keep

A digest is a hash of the exact skill bytes. Pinning records it in a lockfile so that a later update can be compared against what you approved. Without a pin, "it was clean when I installed it" is a memory, not a control.

skillctl status
skillctl explain summarize-notes
skillctl pin summarize-notes

Review the update, not just the install

Most supply-chain attention goes to the first install. The rug pull happens later: a maintainer ships a clean skill, waits, then changes it. When the digest changes, Remit runs a semantic diff and flags changed behavior instead of silently adopting it.

Park or remove what you do not use

A skill that never fires is not neutral. It is context cost and attack surface. skillctl park keeps the evidence but removes the skill from the active set; skillctl uninstall removes it with a record. Neither silently deletes files you installed by hand.

Route instead of loading everything

If your fleet is large, the MCP router is the highest-leverage change: it loads skills on demand and applies the same policy and revocation checks at load time. The measured difference on the build machine was roughly two orders of magnitude in startup context.

Keep a kill switch

The signed feed carries revocations and drift. On the next sync, a revoked digest is blocked by the router and the feed. Remit-managed copies are removed; hand-installed copies are surfaced and parked with a removal note. The point is that a bad update does not require chasing every laptop by hand.

What this audit does not prove

It is worth being blunt, because security tooling rarely is:

  • A finding is a rule match, not proof of intent. A clean scan is not proof that a skill is benign.
  • A canary receipt is one observed run in a container. It is not a guarantee that the skill cannot escape, exfiltrate, or behave differently on another host.
  • The canary is observer-first by default. It enforces egress only when you pass an allowlist, and it sees proxy traffic, not TLS bodies.
  • Static coverage can be partial when files are oversized, opaque, or symlinked. The scan reports that state instead of calling it clean.

The honest framing: this audit tells you what is installed, what it appears able to do, and what changed. It does not certify safety. Use it to decide what to read, pin, or remove — then keep the lifecycle going.

Do it once, then put it on a schedule

A one-time audit is a snapshot. The risks that matter recur: a skill updates, a teammate installs something new, a maintainer changes a repo, a revocation lands. The useful version of this practice is a weekly scan, a digest of what changed, and a clear path to revoke.

Start with the free local audit. If it finds nothing you did not know, you have lost five minutes. If it finds one thing, you have a concrete reason to keep going.
